# Grovebound 병렬 멀티 에이전트 개발 규칙

이 문서는 여러 작업이 같은 저장소에서 안전하게 진행되기 위한 운영 기준이다. 게임 설정은 `PROJECT_SETTINGS.md`, 구현 상태는 `STATUS.md`, 바로 다음 작업은 `NEXT_SESSION.md`가 우선한다.

## 불변 조건
- 기존 게임 설정, 동료 ID·종·특성·옵션·편성·진화 결과와 사용자 저장을 보존한다.
- Godot 4.7 Standard, 모바일 가로 화면, 작은 캐릭터·넓은 시야와 승인된 도트풍을 유지한다.
- 미정인 심층 콘텐츠, 야생 2·3성 분포, 입장 재화 수치는 사용자 승인 없이 구현하지 않는다.
- 자동 검증, 실제 Godot QA, 사람 난이도와 실기기 검증을 서로 바꾸어 설명하지 않는다.

## 역할과 소유권
| 역할 | 기본 소유 영역 | 책임 |
|---|---|---|
| 통합 리드 | `main.gd`, `main.tscn`, `project.godot`, 저장 스키마, 공통 인계 문서 | 계약 승인, 연결, 전체 회귀, 최종 병합 |
| 게임 기획 (Game Designer) | 할당된 `docs/design-reviews/<작업명>.md` | 실제 루프·외부 사례·적합성·수용 기준·사후 검토. 제품 파일은 읽기 전용 |
| 전투·성장 | 전투·AI·합성·승급·진화 모듈 | 독립 규칙과 집중 테스트 |
| 캠페인·데이터 | 캠페인/지역/종/보상 데이터 | 해금·배치·보상 규칙과 테스트 |
| UI·UX | `ui/` | 표시 모델과 사용자 명령, UI 회귀 |
| 아트·모션 | `assets/`, 제품용 `animation/` | 승인 비율·팔레트·실제 속도 검토 |
| QA·릴리스 | `tools/`, 검토 장면, 검사 결과 | 독립 재현, 회귀, 증거와 원격 결과 확인 |

통합 리드 전용 파일은 다른 역할이 직접 고치지 않는다. 필요한 변경은 인수인계의 `통합 요청`에 정확한 호출 지점과 기대 동작으로 남긴다. 한 파일과 한 장면은 한 시점에 한 소유자만 가진다.

## 작업 분리 승인 조건
기획 역할의 상세 기준과 검토 기록 형식은 `agents/GAME_DESIGNER.md` 한 곳에서 관리한다. 기획은 제안자이며 최종 결정·파일 소유권·작업 배분·공통 문서 반영은 총괄이 맡는다. 기획과 QA가 같은 검토 파일을 동시에 수정하지 않는다. QA 증거는 별도 결과나 메시지로 전달하고 기획 기록은 지정 소유자 한 명이 갱신한다.

다음 조건을 모두 만족해야 병렬로 실행한다.
1. 기준 main의 전체 SHA가 같다.
2. 입력·출력 계약과 제외 범위가 기록돼 있다.
3. 쓰기 대상 파일이 겹치지 않는다.
4. 저장 또는 공통 API 변경은 선행 계약 PR로 병합됐다.
5. 각 작업에 독립적인 집중 검사가 있다.

하나라도 만족하지 않으면 선행/후속 PR로 순차 처리한다.

## Worktree·브랜치·PR
1. 통합 리드가 최신 `origin/main` SHA와 작업 그래프를 기록한다.
2. 계약 변경이 있으면 `contract/<이름>` PR을 먼저 병합한다.
3. 병합된 같은 SHA에서 작업마다 별도 worktree를 만든다.
4. 브랜치는 `feat/`, `fix/`, `test/`, `art/`, `contract/`, `integrate/` 접두사를 사용한다.
5. 기능·리팩터링·대규모 에셋 변경을 한 PR에 섞지 않는다.
6. 제품 PR은 통합 리드 전용 파일을 건드리지 않는다. 연결은 `integrate/` PR에서 수행한다.
7. 최신 main 반영, 필수 검사와 인계 확인 후 squash merge한다.
8. 원격 병합 SHA와 CI 결과를 확인한 뒤 worktree를 정리한다.

## Godot 충돌 회피
- `main.tscn`과 같은 공통 씬은 통합 리드만 수정한다.
- 새 기능은 독립 `.gd` 또는 하위 씬으로 만들고 부모 연결은 통합 단계에서 수행한다.
- `.tscn` 충돌을 자동 병합하지 않는다. 먼저 병합된 변경 위에 후속 변경을 Godot에서 재적용한다.
- 편집기를 열고 닫아서 생긴 무관한 직렬화, `.uid`, `.import` 변경을 제거한다.
- 검토 장면과 제품 장면을 분리하고 검토·녹화는 사용자 `user://` 저장을 읽거나 쓰지 않는다.
- Autoload, InputMap, 렌더러나 해상도 변경은 독립 계약 PR과 사용자 승인이 필요하다.

## 검증 게이트
문서만 변경하는 운영 작업은 제품 변경이 없음을 diff로 확인하고 인계·링크·권한 충돌·실제 호출/모의 전달을 검사한다. 이 경우 아래 제품용 Godot/저장/렌더 검사는 적용 대상이 아님을 명시한다. 원격 필수 CI는 문서 작업도 생략하거나 우회하지 않는다. 제품 변경이 섞이면 이 예외를 사용하지 않는다.

### 기능 PR
- Godot import 성공, Parse/SCRIPT ERROR 없음
- 변경 모듈 집중 검사 통과
- 사용자 저장 미사용, 범위 밖 수치 무변경
- 불필요한 장면·에셋 직렬화 변경 없음

### 통합 PR
- 최신 전체 회귀와 `python tools/check_handoff.py` 통과
- 구세이브 로드·저장 왕복·저장 실패 무변경 검사
- 기존 동료와 캠페인 진행 회귀
- 실제 Godot 렌더 검토 1개 이상
- UI·배경은 인게임 스크린샷, 모션은 실제 Godot GIF·MP4
- 미실행 검사와 알려진 경고를 명시
- 원격 CI와 병합 SHA 확인

## 인수인계
기획 사전/사후 판정과 수용 기준 ID, 승인/미정 항목, QA 증거 위치를 PR에 연결한다. 작은 버그는 PR 본문에 간단히 기록하고 별도 기획 문서를 강제하지 않는다.

각 PR은 `.github/pull_request_template.md` 항목을 채운다. 복잡한 작업은 `docs/handoffs/<작업명>.md`에 기준 SHA, 목표/제외, 소유 파일, 계약 변경, 보존 조건, 검사 결과, 미검증, 저장 영향, 위험, 통합 요청과 후속 작업을 남긴다.

## 현행 작업 순서
1. 총괄이 원격 최신 main SHA, 열린 PR·진행 작업·미커밋 변경과 공통 문서/계약/실제 소스를 확인한다.
2. 기획이 작업 유형에 맞춰 사전 검토하고 필요한 외부 사례와 적합성·수용 기준을 전달한다.
3. 총괄이 채택/기각 이유와 범위를 기록한다. 중요한 미정 설정·기획·밸런스 변경은 사용자 승인 후 계약과 문서에 반영한다. 승인 대기 중 종속 구현은 시작하지 않는다.
4. 같은 승인 기준 SHA에서 독립 개발 worktree·브랜치·소유 파일·검사·통합 순서를 배분한다. 의존성이 있으면 순차 실행한다.
5. 작성자와 다른 QA가 독립 검증하고 결함은 파일 소유자가 수정한다. 기획은 수정된 결과를 최초 수용 기준과 실제 증거로 사후 검토한다.
6. 총괄이 전체 회귀·Godot 실행·UI 캡처 등 해당 검증, 필수 CI와 인계를 확인해 PR을 병합하고 원격 main SHA를 확인한다. 사용자 병합 승인이 없는 작업은 PR까지 준비한다.
7. STATUS/NEXT_SESSION을 갱신하고 확정 설정 변경은 PROJECT_SETTINGS에도 반영한다. 미검증은 남긴다.

입장 재화 파일럿은 이전 계획이며 현재 자동 착수할 우선 작업이 아니다. 입장 재화는 기능·밸런스 테스트 마무리 시 별도 요청과 대상/일일량/회복/비용 합의 후 진행한다. 심층도 계속 보류한다. 최신 NEXT_SESSION과 사용자 요청이 작업 우선순위다.

## 실행 환경과 역할 호출
- 이 문서의 역할은 논리적 업무 구분이다. 현재 저장소에는 전용 에이전트 실행기나 영구 역할 등록 설정이 없다. CODEOWNERS는 GitHub 소유권이며 실행기 설정이 아니다.
- 매 Work에서 총괄은 도구 노출 여부·호출 성공·병렬 가능 여부를 각각 확인한다. 지원 시 기획 역할 지시문에 `agents/GAME_DESIGNER.md`, 기준 SHA, 읽을 파일, 소유 파일/읽기 전용 범위, 제외 범위, 산출물과 수용 기준을 전달한다. 개발/QA에도 해당 검토 결과를 명시적으로 전달한다.
- 현재 Work는 collaboration의 spawn_agent/send_message/followup_task로 역할을 지정할 수 있다. 문서 추가로 새 named agent가 등록되거나 모든 환경에서 자동 실행되는 것은 아니다. 향후 실행기가 공식 등록 방식을 제공하면 그 환경의 공식 문서를 확인한 뒤 등록·실제 호출을 별도 검증한다. 검증하지 않은 설정 키를 만들지 않는다.
- 실행 미지원/실패 시 원인·실제 실행 역할·순차 대체를 기록한다. 동일 에이전트의 역할 전환은 독립 QA로 보고하지 않는다. 필요한 독립 검증이 확보되지 않으면 미충족 게이트를 남기고 병합하지 않는다.
